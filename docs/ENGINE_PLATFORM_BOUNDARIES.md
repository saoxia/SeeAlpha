# SeeAlpha：Engine 与 Platform 的职责边界

> 决策日期：2026-11-09。此文档定义长期产品定位和新开发的归属准则，不代表下述独立性验收已完成，也不授权在本次文档变更中迁移代码、数据或启动实盘。

## 产品定位

SeeAlpha = **量化交易能力内核（Engine）** + **量化研发与运营平台（Platform）**。

- **Engine 追求量化能力的上限**：提高行情与数据质量、研究和回测能力、组合风控、模拟与实盘执行、性能和可靠性。
- **Platform 追求使用量化能力的效率**：降低策略开发、验证、发布、管理和运营的门槛，为人工用户与经授权的 AI 工作流提供统一入口。
- **仓库策略（2026-11-10 更新）**：用户已授权渐进拆分；独立 Engine 仓库已建立，原 Monorepo 暂留旧实现和联合测试，Platform 开始接入外部 Engine 服务/固定镜像。此阶段不删除旧 `engine/`，不自动切换实盘。

## 职责归属

| 领域 | 归属 | 判定原则 |
| --- | --- | --- |
| 交易所连接器、行情采集、历史补齐、原始数据校验、Catalog、数据计算 | Engine | 处理交易所协议及量化数据本身 |
| 策略包加载、回测与模拟交易、指标和信号计算、组合协调、交易风控与订单执行 | Engine | 执行量化逻辑，决定运行事实与交易状态 |
| 实时订阅运行、任务实际计算、订单/成交/持仓/风险事件及幂等恢复 | Engine | 运行时事实由 Engine 持有，并提供查询/事件接口 |
| 用户、租户、身份认证、业务授权、账户配置和密钥管理、策略登记与发布授权 | Platform / API | 决定**谁**可以访问与启动**什么** |
| 研究工作流、任务编排、资源与租户实例管理、审批和操作审计 | Platform / API | 管理计算任务，而不是在业务进程内执行量化计算 |
| Web 策略管理与研究界面、报告展示、账户/绩效视图、运营后台 | Platform / Web 与 API | 展示及管理，不包含交易所执行逻辑 |
| 业务账本与对账、用户可见的历史记录及报告索引 | Platform / API | 由 Engine 提供必要的交易所查询及交易事实，Platform 完成业务归档、核算与展示 |
| 跨边界共享的数据模型、错误码和请求/响应定义 | 最小契约层（当前在 `core/`） | 仅保留独立、可版本化的轻量契约；不容纳连接器、Nautilus runtime 或业务逻辑 |

**边界案例**：

- “回测参数编辑、回测请求、进度和报告索引”归 Platform；“读入历史数据、执行回测、计算结果”归 Engine。
- “策略编辑器、AI 研究流程、策略版本及授权”归 Platform；“策略代码校验/隔离执行、加载与运行”归 Engine。
- “行情采集任务配置与授权”归 Platform；“行情采集、修复、存储与健康事实”归 Engine。
- “交易所资产/资金流水的原生读取”归 Engine；“账户汇总、业务账本与对账”归 Platform。现有残余直接依赖应按独立迁移清单消除，**不得**在业务端复制 Connector。

## 运行与依赖原则

1. **依赖方向**：生产 Platform 通过已认证、可版本化的服务契约调用 Engine；Engine 不 import `api/`、`web/`，不依赖业务 ORM、用户表或 UI。不得以改名 import 或把实现移入 `core/` 冒充解耦。
2. **控制与计算分离**：启动/停止、回测提交、策略下发、状态和报告查询可经 HTTP；大规模历史数据直接由 Engine 从其获授权的数据卷读取，避免每次请求跨服务搬运全部数据。未来若需异步任务或事件流，先按性能和可靠性需求设计，不默认添加新的中间件。
3. **租户与权限**：Platform 决定授权与实例分配；Engine 验证固定租户身份、账户与请求授权。开发与正式用途保持隔离；AI/不可信代码不得直接获得生产交易权或 Docker 管理权限。
4. **运行事实与业务事实分离**：Engine 维护运行状态、订单幂等、成交、持仓及恢复；Platform 维护用户/租户/授权、业务记录和聚合视图。断连应报告失败，不允许暗中回退到本地实盘执行。
5. **独立生命周期**：一个 Platform 可管理多个具有独立资源、数据和运行状态的 Engine；Engine 的版本与平台版本通过明确的兼容契约配合。容器资源限制并不等于不可信策略的安全沙箱。
6. **开发便利不改变生产边界**：Monorepo 可共享 CI、开发依赖和测试用例，但正式构建产物与运行依赖必须保持隔离；历史本地测试入口不得成为生产路径。

## 当前状态（不是完成宣告）

截至 2026-11-09，仓库已有 `engine/`、`api/`、`web/`、`core/` 和策略 `packages/`；Engine 有单独启动入口和独立 Docker 镜像，且支持按租户管理 Engine 容器。当前 Docker 模式为可选，同宿主机部署，不包含跨服务器调度或不可信策略安全沙箱。

2026-11-09 的第 8–14 项已消除生产 Platform 对 Engine 与 NautilusTrader 源码的直接导入，并验证隔离环境下的跨进程 HTTP 契约、租户权限与独立 Engine Docker 构建（[PR #38](https://github.com/saoxia/SeeAlpha/pull/38)）。**达到这一阶段的源码与构建隔离，不等于已拆为独立仓库，也不等于具备真实资金实盘或不可信代码安全沙箱能力**。

尚待独立验收：真实账户与真实交易所链路、策略运行时可靠性、长期行情采集、状态卷备份恢复，以及多版本发布兼容矩阵。当前处于独立仓库迁移过渡期，仍保留 Monorepo 与同机可选 Docker 模式；新启动流程见 [跨仓库接入](EXTERNAL_ENGINE.md)。具体边界与历史变更见 [Engine 仓库边界](ENGINE_REPOSITORY_BOUNDARY.md)，存储及租户路由见 [每租户 Docker Engine](TENANT_DOCKER_RUNTIME.md)。

## 独立仓库就绪的验收标准

只有满足以下条件，才能说 Engine 已具备独立仓库能力；满足后也**不要求立即拆仓**。

1. 生产 API 的所有模块在没有 Engine 源码和 NautilusTrader runtime 的环境中可导入、启动并管理业务；访问不可用 Engine 时返回明确错误（例如 503），不静默退回本地执行。
2. Engine 可仅凭其源码、锁定依赖、契约及已授权的运行配置独立构建、启动，镜像不包含业务 API、Web 或业务数据库迁移源码。
3. 策略包下发、回测、行情及历史任务、账户查询、模拟/受控交易指令均通过明确的跨进程契约验收；保留精度、幂等、风险门禁、租户隔离与异常恢复测试，不因测试通过宣称已完成真实资金实盘验收。
4. API/Engine 的契约具备版本或兼容性策略，验证不同支持版本的请求、结果和错误语义。
5. 独立状态卷与数据卷、备份和恢复流程明确，不因升级丢失订单、成交、持仓、幂等事实或租户归属。

## 实施顺序与范围约束

1. 优先清理业务 API 直接使用交易所连接器的只读查询；保持账户与交易事实的业务归档归 Platform。
2. 然后处理操作记录/资产对账所需的 Engine 查询与事件契约。
3. 最后清理市场数据管理、策略包校验和其他 API → Engine 内部实现引用，并执行跨进程回归验收。
4. 在确有维护与发布收益之前，不拆仓、不引入共享数据服务、不复制每租户数据，也不主动改变当前部署默认模式。

每一步均为**后续独立任务**，须按 [开发规范](../AGENTS.md) 的架构冻结、最小变更与验证规则分别实施。此文档仅确立目标，不表示以上改造已经实施。
